# Test Cases: Firestore Read Optimizations (Recent Changes)

วันที่ปรับปรุงเอกสาร: 2025-09-23
ขอบเขต: ทดสอบการแก้ไขล่าสุดที่เพื่อลดจำนวน Firestore reads และปรับปรุง UX ในหน้าแชท
- ลดจำนวนข้อความที่โหลดใน `ChatScreen` (เริ่มที่ 100, เพิ่มครั้งละ 100, สูงสุด 300)
- ปรับ `ChatController._augmentAssignees` ให้ดึงชื่อผู้รับผิดชอบแบบ batch + cache (พร้อมเก็บลำดับ) และลบโค้ดที่ไม่ใช้

## 1) รายการเปลี่ยนแปลง (Scope)
- ChatScreen
  - `_messageLimit` = 100
  - `_loadMoreStep` = 100
  - `_maxMessageLimit` = 300
- ChatController
  - ใช้ `UserCacheService` เพื่อดึงชื่อผู้ใช้ทีละชุด (whereIn + chunk) และ cache ในหน่วยความจำตลอด session
  - ลบตัวแปรท้องถิ่นที่ไม่ถูกใช้งาน (แก้ lint)

## 2) Test Data Setup
- มี Chatroom อย่างน้อย 1 ห้องใน workspace ทดสอบ
- ห้องแชทควรมีจำนวนข้อความแตกต่างกัน: ~50, ~120, ~220, >320 เพื่อครอบคลุมทุกขอบเขต
- เตรียมผู้ใช้ (sales) 2-4 คนใน collection `users` โดยมีฟิลด์ `displayName` หรือ `name` เพื่อใช้ทดสอบการแสดงผลชื่อ
- สถานะห้อง (IN_PROGRESS/DONE), การผูก customer (มี/ไม่มี) ทั้งสองแบบ

## 3) Test Cases — ChatScreen (ลดจำนวนข้อความที่โหลด)

### TC-CS-001: โหลดครั้งแรกจำกัด 100 ข้อความ
- Preconditions: ห้องแชทมี ≥ 100 ข้อความ
- Steps:
  1) เปิดหน้า Chat สำหรับห้องเป้าหมาย
  2) สังเกตว่ารายการข้อความแสดงเฉพาะ 100 รายการล่าสุด (เรียงจากใหม่ไปเก่า)
- Expected:
  - จำนวนข้อความใน List เท่ากับ 100 (ถ้ามีมากกว่า 100)
  - UI ไม่กระตุก, ไม่มี error ใน console

### TC-CS-002: เลื่อนขึ้นเพื่อโหลดเพิ่ม +100
- Preconditions: ห้องแชทมี ≥ 200 ข้อความ
- Steps:
  1) จากสถานะเริ่มต้น (100 ข้อความ) เลื่อนขึ้นจนถึงบริเวณด้านบนของรายการ
  2) รอให้โหลดเพิ่มเสร็จ
- Expected:
  - จำนวนข้อความเพิ่มเป็น 200 รายการ
  - Scroll position ถูกรักษา (ไม่กระโดดผิดตำแหน่ง)

### TC-CS-003: จำกัดสูงสุด 300 ข้อความ
- Preconditions: ห้องแชทมี > 320 ข้อความ
- Steps:
  1) ทำซ้ำการเลื่อนขึ้นเพื่อโหลดเพิ่มจนถึง 300 รายการ
  2) พยายามเลื่อนขึ้นต่อเพื่อให้โหลดเกิน 300
- Expected:
  - จำนวนข้อความไม่เพิ่มเกิน 300
  - หากมีฟีเจอร์โฟกัสข้อความอ้างอิง (reply) ไปยังข้อความเก่ามาก ๆ ที่อยู่นอกช่วง 300: ระบบแสดงข้อความแจ้งเตือน (เช่น "ไม่พบข้อความต้นฉบับ") หรือพยายามโหลดเพิ่มจนแตะเพดาน 300 แล้วจึงแจ้งเตือน

### TC-CS-004: Auto-scroll เมื่อมีข้อความใหม่เข้ามา
- Preconditions: เปิดหน้าแชทและอยู่ใกล้ท้ายรายการ (near bottom=true)
- Steps:
  1) ส่งข้อความใหม่จากผู้ใช้ปัจจุบัน หรือให้ผู้ใช้อีกคนส่งเข้ามา
- Expected:
  - ถ้า near bottom และไม่อยู่ในโหมดค้นหา, รายการเลื่อนอัตโนมัติไปท้ายสุด
  - ถ้าข้อความใหม่เป็นของตัวเอง อาจใช้การ jump เพื่อลดการกระตุก (behavior เดิมยังคงอยู่)

### TC-CS-005: ค้นหาในแชทยังคงทำงาน
- Steps:
  1) เปิดแถบค้นหา
  2) พิมพ์คำค้นหาให้มีผลลัพธ์บางส่วนในช่วง 100/200/300
- Expected:
  - ไฮไลต์ผลลัพธ์, เลื่อนโฟกัสถัดไป/ก่อนหน้าได้ตามปกติ
  - ผลการค้นหาจำกัดในข้อความที่โหลดแล้ว (ขึ้นอยู่กับจำนวนที่โหลด ณ ตอนนั้น)

### TC-CS-006: โฟกัสข้อความอ้างอิง (Reply) ที่อยู่นอกช่วง
- Preconditions: มีข้อความ reply ไปยังข้อความต้นฉบับที่เก่ามาก
- Steps:
  1) แตะที่ preview ของ reply เพื่อโฟกัสไปยังข้อความต้นฉบับ
- Expected:
  - ระบบพยายามเพิ่ม `_messageLimit` เป็นช่วง ๆ (ทีละ 100) จนเจอข้อความต้นฉบับ หรือจนถึงเพดาน 300
  - ถ้าไม่พบเมื่อถึง 300 จะแจ้งเตือนผู้ใช้อย่างเหมาะสม

### TC-CS-007 (ทางเลือก): ตรวจสอบจำนวน Firestore Reads
- Tools: Firebase Console > Usage หรือ Emulator + Logs
- Steps:
  1) เปิดห้อง 1 ครั้ง (100 รายการ)
  2) เลื่อนโหลดเพิ่ม 2 ครั้ง (200, 300)
- Expected:
  - จำนวน reads ต่อห้องลดลงเมื่อเทียบกับเวอร์ชันก่อนหน้า (ที่เคยโหลด 500)

## 4) Test Cases — ChatController (หาชื่อ assignees แบบ batch + cache)

> ครอบคลุมทั้งกรณีมี/ไม่มีการผูก customer

### TC-CC-001: กรณีมีการผูก customer — ดึงชื่อแบบ batch
- Preconditions:
  - customer doc ใน workspace มีฟิลด์ `assignees: [uid1, uid2, ...]`
  - เอกสารผู้ใช้มี `displayName` หรือ `name`
- Steps:
  1) เปิดหน้าที่แสดงรายชื่อแชท/รายการที่เรียก `_augmentAssignees`
- Expected:
  - ชื่อผู้รับผิดชอบแสดงครบและเรียงตามลำดับ uid ที่กำหนด
  - ไม่มีการยิง `.get()` ทีละ uid เป็นรอบ ๆ (ควรเห็น batch/whereIn ใน logs)

### TC-CC-002: กรณีไม่มีการผูก customer — ใช้ `chatroom.assignees`
- Steps:
  1) สำหรับห้องที่ไม่มี customer ให้กำหนด `assignees` ที่ระดับ chatroom
  2) เปิดรายการที่เรียก `_augmentAssignees`
- Expected:
  - ใช้ข้อมูล `assignees` จาก chatroom โดยตรง (ไม่มี fallback `.get()` ห้องอีกครั้ง)
  - แสดงชื่อที่แก้ไขเป็นแบทช์เหมือนกัน

### TC-CC-003: Cache — เปิดซ้ำควรไม่ยิงอ่านซ้ำ uid เดิม
- Steps:
  1) เปิดหน้ารายการที่เรียก `_augmentAssignees` ครั้งที่ 1
  2) กลับออกแล้วเปิดใหม่ภายใน session เดิม
- Expected:
  - ครั้งที่ 2 ไม่ขออ่าน Firestore สำหรับ uid ที่เคยโหลดแล้ว (ตรวจจาก logs/metrics)

### TC-CC-004: ข้อมูลไม่ครบถ้วน — fallback เป็น uid
- Steps:
  1) ตั้งค่า user บางคนไม่มี `displayName`/`name`
- Expected:
  - แสดง uid แทนค่าชื่อที่ว่าง, ไม่มี error

### TC-CC-005: ความทนทาน — บาง uid หาไม่เจอ
- Steps:
  1) ใส่ uid ที่ไม่มีใน collection `users`
- Expected:
  - แสดงชื่อผู้ใช้ของ uid ที่เหลือได้ปกติ, uid ที่ไม่เจอ fallback เป็นตัว uid เอง, ไม่มี crash

## 5) Non-Functional & Regression
- ไม่มีการเพิ่ม Stream/Listener ซ้ำซ้อนในหน้าเดียวกัน (หลีกเลี่ยงการฟังเอกสาร chatroom ซ้ำ ๆ)
- Build/Lint ผ่าน (ไม่มี error ที่ block การ build; มีเพียง warning ของฟังก์ชัน/เมธอดที่ยังไม่ถูกใช้งาน ซึ่งไม่กระทบการทำงาน)
- ประสิทธิภาพ/ค่าใช้จ่าย: จำนวน reads โดยรวมลดลงเมื่อใช้งานจริง (โดยเฉพาะห้องที่มีข้อความจำนวนมาก)

## 6) วิธีตรวจสอบ/เครื่องมือ (แนะนำ)
- Firebase Console > Usage (ดู Read count รายวัน)
- Emulator + verbose logs ของแอป (ดูการ query whereIn และจำนวนครั้งที่เกิดขึ้น)
- Flutter DevTools (performance, memory)

## 7) Acceptance Criteria
- เปิดห้องครั้งแรกแสดง 100 ข้อความล่าสุดได้ถูกต้อง และเลื่อนเพื่อโหลดเพิ่มเป็น 200/300 ได้ตามลำดับ
- ระบบไม่โหลดเกิน 300 ข้อความ และจัดการกรณีโฟกัสข้อความที่อยู่นอกช่วงได้เหมาะสม (แจ้งเตือน)
- รายชื่อผู้รับผิดชอบแสดงถูกต้องทั้งกรณีมี/ไม่มี customer และมีการใช้ cache ลดการอ่านซ้ำ
- ไม่มี error ใน runtime/console; lint/blocking error เป็นศูนย์
